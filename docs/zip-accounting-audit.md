# 1. Як працює зараз

## 1.1 Модель даних

**Аркуш-категорія** (рядки 1–3 — шапка, дані з рядка 4; GAS-ЗІП:72 читає `getRange(4, 1, lastRow-3, 11)`):

| Кол. | Індекс у коді | Вміст | Роль в обліку |
|---|---|---|---|
| A | `row[0]` | № | довідково |
| B | `row[1]` | Модель / Тип | **ключ позиції** (текстом) |
| C | `row[2]` | Обладнання | довідково |
| D | `row[3]` | Мінімальний залишок | **точка замовлення** |
| E | `row[4]` | Залишок (поточний) | **єдине джерело залишку** |
| F | — | Дата використання (накопичувальний текст) | довідково |
| G | — | Кількість (накопичувальна сума) | довідково |
| H | — | Де було використано (накопичувальний текст) | довідково |
| I | `row[9]`* | «Залишок на \_\_.\_\_.2026» або Постачальник | довідково |
| J | `row[10]`* | Постачальник або Телефон | у лист |
| K | — | Телефон | у лист |

\* Індекси в коді фіксовані (`supplierName: row[9]`, `supplierPhone: row[10]` — GAS-ЗІП:87–88), а фактична кількість колонок різна на різних аркушах. Див. проблему **P0-6**.

**Аркуш `Лог_використання`** (GAS-ЗІП:154–163): `Час запису | Дата використання | Категорія | № | Модель/Тип | Механік | Де використано | Кількість`. Записуються **лише видачі** — інших типів операцій у системі немає.

## 1.2 Залишок: звідки береться

Залишок **не рахується** — він зберігається в комірці E і переписується на місці (GAS-ЗІП:166–170):

```js
const stockCell = targetSheet.getRange(payload.row, 5); // Колонка E
const minStock  = targetSheet.getRange(payload.row, 4).getValue(); // Колонка D
const currentVal = Number(stockCell.getValue()) || 0;
const newVal = currentVal - Number(payload.quantity);
stockCell.setValue(newVal);
```

Формула: **`E_new = E_old − q`**, де `q` — кількість із форми додатка.

Паралельно додаток зменшує свою локальну копію і кладе її в кеш браузера (APP:881–884):

```js
itemInArray.currentStock = (parseFloat(itemInArray.currentStock) - qty).toString();
localStorage.setItem(CACHE_KEY, JSON.stringify(allData));
```

Ключовий наслідок: **E — не похідна від журналу, а окреме число**. Прихід товару, повернення, виправлення помилки, інвентаризація вносяться руками прямо в E і не лишають жодного сліду. Журнал і залишок можуть розійтися як завгодно, і жоден механізм цього не виявляє.

## 1.3 Витрата: три різні числа в трьох місцях

1. **Журнал** `Лог_використання` — повний перелік видач (GAS-ЗІП:154–163).
2. **Накопичувальні F / G / H** (GAS-ЗІП:173–187): `qtyCell.setValue(oldQty + payload.quantity)`. Період не визначений: меню «🧹 Очистити дані списань» обнуляє F, G, H на всіх аркушах (GAS-ЗІП:27, `getRange(4, 6, lastRow-3, 3).clearContent()`). У шапці таблиці ці колонки досі підписані «Використано протягом квітня», хоча містять серпневі дані.
3. **`usage30Days`** — єдине число, що впливає на замовлення (GAS-ЗІП:209–223):

```js
const thirtyDaysAgo = new Date();
thirtyDaysAgo.setDate(thirtyDaysAgo.getDate() - 30);
for (let i = 1; i < logData.length; i++) {
    const logDate = new Date(logData[i][0]);          // колонка A — час запису
    if (logDate >= thirtyDaysAgo) {
        const key = logData[i][2] + "_" + logData[i][4];   // Категорія_Модель
        usage30Days[key] = (usage30Days[key] || 0) + (Number(logData[i][7]) || 0);
    }
}
```

Отже витрата = сума кількостей за журналом, з ключем **(назва аркуша, текст моделі)**, у вікні 30 днів **за часом створення запису** (колонка A), а не за датою операції (колонка B).

## 1.4 Точка замовлення

Правило одне й те саме у двох місцях — **`залишок ≤ мінімум`**:

```js
// GAS-ЗІП:190 — миттєвий тригер листа після видачі
if (newVal <= Number(minStock)) { sendPurchasePlan(false); }

// GAS-ЗІП:258 — відбір рядків у звіт
if (currentStock <= minStock) { needsOrder = true; ... }
```

Мінімум `D` — константа, введена людиною. Він не переглядається, не залежить від часу поставки, від фактичної витрати і від критичності вузла. У додатку те саме правило підсвічує картку червоним (`isLowStock = parseFloat(item.currentStock) <= parseFloat(item.minStock)`).

## 1.5 Обсяг замовлення

GAS-ЗІП:266–267:

```js
let recommendBuy = Math.max((minStock - currentStock), used30);
if (recommendBuy === 0) recommendBuy = 1;
```

Формула: **`Q = max(D − E, U30)`**, а якщо вийшов нуль — **`Q = 1`**.

Одиниця в листі захардкоджена: `${used30} шт.` і `${recommendBuy} шт.` (GAS-ЗІП:275–276).

## 1.6 Коли надсилається лист

| Тригер | Код | Частота |
|---|---|---|
| Після кожної видачі, що лишила залишок ≤ мінімуму | GAS-ЗІП:190–192 | скільки видач — стільки листів |
| Кнопка «Відправити план закупки» в додатку | APP:527 (пароль `5588` перевіряється **у браузері**) → `?action=forceReport` → GAS-ЗІП:121–124 | вручну |
| Щопонеділка о 08:00 | GAS-ЗІП:306–318 | якщо тригер створено |

## 1.7 Наскрізний приклад на реальному рядку

Підшипник **6200-2RSH** (аркуш «Підшипники», рядок 4 таблиці): `D = 10`, `E = 4`.
Журнал за 30 днів: 21.08 — 7 шт, 21.08 — 5 шт → `U30 = 12`.

* Потрапляє у план: `4 ≤ 10` ✓
* `Q = max(10 − 4, 12) = 12`
* Після поставки на складі буде 16 при мінімумі 10.

Обидві видачі 21.08 — це **одна заміна натяжних роликів**. Система читає їх як місячну норму споживання і закладає таку саму витрату на наступний місяць.

Відтворення `sendPurchasePlan()` на знімку таблиці від 22.08.2026:

| Показник | Значення |
|---|---|
| Позицій з назвою моделі | **251** |
| Потрапляє в кожен план закупки (`залишок ≤ мінімум`) | **189 (75 %)** |
| з них справжній дефіцит (`залишок < мінімум`) | 85 — з яких 42 лише через непорахований аркуш «ЗІП» |

| з них порожні / нечислові рядки (мін = 0 і залишок = 0) | 2 |

| Сумарний обсяг рекомендації | **382 од.** |

Розподіл по аркушах (у плані / всього): Підшипники 11/24 · Сальники та Кільця 17/32 · Торцеві ущільнення 4/12 · Молочне з'єднання 5/7 · Клампове ущільнення 5/9 · **Електричні запчастини 50/51** · **Інструменти 30/31** · Мастильні матеріали 6/16 · Розхідні до принтерів 1/4 · Контейнер та приміщення 16/19 · **ЗІП 42/42** · ЗІП для ХВО 2/4.

Конкретні наслідки, які видно просто зараз:

* **Інструменти.** 30 з 31 рядка (`мін = 1`, `залишок = 1`) щоразу потрапляють у план із рекомендацією «замовити 1 шт»: зварювальний апарат, свердлильний верстат, гідравлічний прес, набори ключів. Це основні засоби, а не витратний ЗІП, і вони не мають бути в логіці поповнення взагалі. Єдиний рядок, що не потрапив — «Електропила Дніпро-М», і саме тому, що в мінімумі стоїть текст `2 (1+1)`, який перетворюється на 0 (див. **P1-5**).
* **Аркуш «ЗІП» (фасувальні та етикетувальні лінії).** Колонка «Залишок» порожня в усіх 42 рядках → всі 42 позиції в кожному листі, з рекомендацією на рівні мінімуму (разом 99 од. — чверть усього плану).
* **Підшипник 6207** (№8): у мінімумі й залишку стоїть `-` → обидва читаються як 0 → `0 ≤ 0` → позиція у плані назавжди, рекомендація «1 шт».
* **«Квацювання»** (аркуш «ЗІП для ХВО») — це процес, а не деталь; порожні мінімум і залишок → теж у плані з «1 шт».
* **Надлишки не бачить ніхто.** DN-50 (Молочне з'єднання): 122 шт при мінімумі 10; DN-85 (Клампове): 36 при 10. Система дивиться лише вниз від мінімуму.

Практичний підсумок: лист, у якому 189 рядків і 103 з них — вигадана «1 шт», не читають. Реальні 85 дефіцитів тонуть у шумі.

# 3. Проблеми за пріоритетом

## P0 — руйнують достовірність даних

**P0-1. Залишок неможливо відновити з журналу.**
Де: GAS-ЗІП:166–170 (єдина операція `registerUsage`).
Журнал містить лише видачі. Прихід, повернення, виправлення й інвентаризація вносяться руками в колонку E без сліду. Тому `E ≠ f(журнал)` і жодна перевірка неможлива: якщо число розійшлося з полицею, ніхто не дізнається, коли й через що. Це фундамент, на якому тримаються всі інші похибки.

**P0-2. У додатку в журнал пишеться не той механік.**
Де: APP:131–133.
```html
<option value="Гора Андрій Олександрович">Гора Андрій</option>
<option value="Галагін Євгеній Ярославович">Галагін Евгеній</option>
<option value="Сабадаш Геннадій Петрович">Бузницький Юрій</option>
```
Механік обирає «Бузницький Юрій» — у журнал іде **«Сабадаш Геннадій Петрович»**. «Свінцов Михайло» зі списку зник. Наслідок: персональна відповідальність за списання недостовірна, а фільтр «Мої за сьогодні» (порівняння `record.mechanic === mechanic`) не знаходить власних записів. У журналі вже видно наслідок попередньої зміни підписів: одна людина фігурує як «Галагін Евгеній» і як «Галагін Євгеній Ярославович».

**P0-3. Гонка одночасних записів.**
Де: GAS-ЗІП:168–170. Класична схема read-modify-write без `LockService`. Два механіки, що списують одночасно, читають те саме `currentVal`; другий запис затирає перший. Втрата тиха: у журналі два рядки, у залишку — одне віднімання.

**P0-4. Позиція адресується номером рядка.**
Де: APP:838 (`row: currentSelectedItem.row`) → GAS-ЗІП:166.
`row` фіксується в момент завантаження даних (`row: i + 4`, GAS-ЗІП:81) і зберігається в кеші браузера. Вставка або сортування рядка, видалення позиції, застаріла офлайн-черга — і списання зменшує залишок **сусідньої деталі**, тоді як у журнал пишеться модель, узята з клієнта. Журнал і таблиця розходяться, і розбіжність виглядає як «хтось помилився».

**P0-5. Клієнт не бачить помилок сервера; офлайн-черга дублює й губить.**
Де: APP:859 (`mode: 'no-cors'`), APP:403–424.
Відповідь непрозора, тому додаток показує «Успішно списано» навіть тоді, коли скрипт упав. У черзі:
```js
try { await fetch(GOOGLE_SCRIPT_URL, { mode:'no-cors', ... }); }
catch (e) { newQueue.push(item); }
```
Запис прибирається з черги, щойно `fetch` завершився — навіть якщо сервер повернув помилку (**тиха втрата**). І навпаки: якщо запит дійшов, а мережа обірвалась на відповіді, запис лишається в черзі й надсилається вдруге (**подвійне списання**). Ідентифікатора операції немає, тож дублікат неможливо відрізнити.

**P0-6. Зсув колонок постачальника на аркуші «Підшипники».**
Де: GAS-ЗІП:87–88 і 261–262 (`row[9]`, `row[10]`).
На 10 з 13 аркушів є колонка «Залишок на \_\_.\_\_.2026», на «Підшипниках» її немає. Тому там постачальник стоїть у колонці I, а код читає J і K. Результат: у додатку й у листі для всіх підшипників у полі «Постачальник» стоїть телефон, а телефон порожній.

## P1 — систематично хибний обсяг і момент замовлення

**P1-1. `≤` замість `<` плюс примусова «1».**
Де: GAS-ЗІП:258 і 267. Позиція рівно на мінімумі має дефіцит 0, але потрапляє в план, і нульова рекомендація підміняється одиницею. Це джерело 103 фальшивих рядків із 189.

**P1-2. `max(дефіцит, витрата за 30 днів)` — величини різної природи.**
Де: GAS-ЗІП:266. `D − E` — це запас (скільки бракує зараз), `U30` — потік (скільки з'їли за місяць). Максимум із них не має інвентарного сенсу: він не залежить ні від часу поставки, ні від того, коли буде наступний перегляд. Замовлення на 12 підшипників після разової заміни роликів — прямий наслідок.

**P1-3. Немає поняття «вже замовлено».**
Рекомендація рахується тільки від залишку. Поки товар їде, кожен наступний лист повторює ту саму цифру — і, за тригером із GAS-ЗІП:190, приходить після кожної видачі.

**P1-4. Порожній залишок дорівнює нулю.**
Де: GAS-ЗІП:86 і 256 (`Number(row[4]) || 0`). «Не порахували» й «немає на складі» — це одне й те саме число. Весь аркуш «ЗІП» (42 позиції) через це в кожному листі.

**P1-5. Нечислові мінімум і залишок мовчки стають нулем.**
`-`, порожньо, `2 (1+1)` → `Number(...) || 0` → 0. Позиція або назавжди в плані (`0 ≤ 0`), або назавжди поза ним (мінімум 0 при живому залишку). Тихо, без жодного попередження.

**P1-6. Лист після кожної видачі.**
Де: GAS-ЗІП:190–192. Десять списань — десять однакових листів на 189 рядків. Квота `MailApp` (100 листів/добу для звичайного акаунта) вичерпується; після цього `sendPurchasePlan` кидає виняток усередині `doPost`, який ловить `catch` — списання пройде, лист не піде, і ніхто про це не дізнається (через `no-cors` клієнт бачить «успішно»).

**P1-7. Вікно 30 днів рахується не за датою операції.**
Де: GAS-ЗІП:217 (`new Date(logData[i][0])` — колонка A, час створення запису). Списання, датоване механіком заднім числом, потрапляє у вікно за часом внесення. Дві дати в журналі живуть окремими життями.

**P1-8. «Мої за сьогодні» показує неправду на двох рівнях.**
Де: GAS-ЗІП:107 (`historyArr.length < 100`) і APP:711.
Сервер віддає лише 100 останніх записів, фільтрація йде на клієнті — при активній роботі сьогоднішні записи випадають із вікна. До того ж «сьогодні» рахується в UTC:
```js
const todayStr = new Date().toISOString().split('T')[0];
```
Після 21:00 за Києвом (літній час) UTC-дата вже завтрашня: вечірня зміна не бачить своїх списань, а дата операції за замовчуванням (APP:797) підставляється завтрашня. Механік, який не побачив свого запису, робить його ще раз.

## P2 — не враховані сценарії

Розгорнуто в розділі 4: повернення, часткове списання, нульовий залишок, зміна одиниць виміру, комплекти.

## P3 — гігієна й безпека

* **Пароль у браузері.** `if (pwd !== '5588')` (APP:527) — перевірка на клієнті; сам `?action=forceReport` не захищений нічим. Це прямо суперечить власному правилу проєкту в `CLAUDE.md`: «PIN співробітників ніколи не потрапляє в браузер».
* **Відкритий ендпоінт.** URL веб-застосунку лежить у публічному репозиторії (APP:271); `doPost` не перевіряє ані автора, ані вміст. Будь-хто може списати будь-яку кількість із будь-якого рядка або спамити листами через `forceReport`.
* **Сміття в журналі.** Запис від 21.08.2026: категорія «нова категорія», позиція «нова позиція», кількість **1300**. Зараз на план не впливає лише тому, що такого аркуша в таблиці більше немає — тобто в журналі є рядки-сироти, а валідації кількості немає взагалі. Якщо аркуш із такою назвою з'явиться, рекомендація буде 1300 одиниць.
* **Дублі рядків з однаковою моделлю.** Ключ витрати — `Категорія_Модель` (GAS-ЗІП:219), а модель повторюється: «Сальник 15 x 30 x 7» стоїть у рядках 1 і 13, «Сальник 25 x 40 x 7» — у 9 і 11, «210K-32 CAR/SIC/V 1PCS» — у 7 і 9, на аркуші «ЗІП» «Датчик наявності пляшки FA17/BP-0ENBK» — тричі, «Фотодатчик SU-02XP» — чотири рази. Витрата однієї позиції приписується всім однойменним рядкам одночасно, а фізичний запас однієї деталі поділено на кілька незалежних мінімумів.
* **Понеділковий тригер завжди щось надсилає.** `ScriptApp.newTrigger("sendPurchasePlan")` (GAS-ЗІП:314) передає в функцію об'єкт події як `isManual`, тому гілка `else if (isManual)` спрацьовує завжди — щопонеділка приходить або план, або лист «План закупки пустий».
* **Невідомі дії ігноруються мовчки.** `doPost` обробляє лише `registerUsage` (GAS-ЗІП:138); будь-що інше не робить нічого і не повідомляє про це.

# 4. Сценарії, які не враховані

## 4.1 Повернення

**Зараз:** операції не існує. Механік узяв 2 підшипники, поставив 1, другий повернув на полицю — вибору немає: або не записувати нічого (тоді залишок занижений назавжди), або дописати в E руками (тоді журнал показує витрату 2, а `U30` завищений удвічі).

**Наслідок для замовлення:** `U30` систематично завищений на величину неповернень, а `Q = max(D − E, U30)` бере цей максимум — переплата стабільна й непомітна.

**Треба:** тип операції «Повернення» (+ до залишку, окремий рядок журналу) з ознакою стану — придатне на полицю чи брак на списання. Для планування попит рахувати як **видача − повернення придатних**.

## 4.2 Часткове списання

**Зараз:** одна форма — «скільки взяв». Немає різниці між «видано зі складу» і «фактично встановлено». Немає резервування під заплановану роботу. Дробові кількості формально проходять (`parseFloat`), але вся логіка рекомендації цілочисельна за замовчуванням, а `if (recommendBuy === 0) recommendBuy = 1` округлює будь-який залишок дефіциту до одиниці: для «полотна силіконового» чи стрічки конвеєра, які ріжуть на метри, це безглузда цифра.

**Треба:** дві події замість однієї («видано під роботу» → «використано / повернено»), або принаймні дозволити коригувальний запис до тієї самої операції з посиланням на неї (`op_id`).

## 4.3 Позиція з нульовим залишком

**Зараз** три різні ситуації нерозрізненні:
1. справді 0 на полиці (порахували);
2. порожня комірка — ніколи не рахували (весь аркуш «ЗІП», 42 позиції);
3. `-` — позиція не використовується (підшипник 6207, «Колоїд не використовується»).

Усі три дають `Number(...) || 0` і всі три потрапляють у план. Плюс окремий випадок — **від'ємний залишок**: додаток дозволяє перевитрату після підтвердження (APP:830), сервер не обмежує нічим. При `E = −3` і `D = 2` дефіцит рахується як 5. Від'ємне число — це сигнал, що облік розійшовся з реальністю, але жоден механізм на нього не реагує.

**Треба:** окремий статус позиції (`активна` / `не використовується` / `не інвентаризована`); заборона від'ємного залишку без операції «Коригування» з причиною; порожня комірка ≠ 0 — така позиція не потрапляє в рекомендацію, а потрапляє в список «потребує інвентаризації».

## 4.4 Зміна одиниць виміру

**Зараз:** колонки одиниць немає взагалі. У листі захардкоджено «шт.» (GAS-ЗІП:275–276), хоча в таблиці вже змішані одиниці: на аркуші «Мастильні матеріали» шапка мінімуму — «л, шт.», а поруч позиції «в кг» («Харчове мастило PARALIQ GA-351 (в кг)», «Паста для чищення рук WURTH (в кг)»). Найбільша рекомендація в поточному плані — «Олива гідравлічна DIMOIL ІГП-30: мінімум 70, залишок 20 → замовити 50 **шт**», хоча це літри.

Якщо одиницю змінити (пакування по 10 → штуки, кг → літри), історія в журналі лишається в старій одиниці, а `usage30Days` підсумує старі й нові рядки в одну купу — попит вийде беззмістовним, і помилку буде видно лише через кілька місяців.

**Треба:** колонки `Одиниця`, `Кратність пакування`, `Мінімальна партія`; одиниця пишеться **в кожен рядок журналу**; агрегація тільки в межах однієї одиниці; зміна одиниці = нова позиція або явний коефіцієнт перерахунку з датою набуття чинності.

## 4.5 ЗІП, що використовується комплектом

**Зараз:** поняття комплекту немає. Заміна вузла — це 2 підшипники + сальник + ремінь + кріплення — робиться чотирма окремими списаннями, кожне з яких (за GAS-ЗІП:190) може згенерувати власний лист. Попит на пов'язані деталі рахується незалежно, тому їхні мінімуми розходяться: підшипники є, ременя немає — ремонт усе одно неможливий, хоча формально дефіциту в плані не було.

Аркуш «ЗІП» побудований саме як набори під конкретне обладнання («Фасувальна лінія А», «Етикетувальна лінія В» …), з наскрізною нумерацією 1…N у кожному блоці — тобто комплектність у таблиці **мислиться**, але ніде не описана машинно.

**Треба:** довідник комплектів (`комплект → компонент → кількість на комплект`); видача комплекту — одна операція, що породжує N подій по компонентах зі спільним `op_id`; попит планується на рівні компонентів, а достатність — на рівні комплекту («скільки комплектів можна зібрати з наявного»), бо саме ця цифра відповідає на питання «чи зможемо полагодити лінію завтра».

# 5. Рекомендована цільова логіка

## 5.1 Принцип

**Журнал операцій — єдине джерело правди; залишок — обчислюване значення.**

```
Залишок(позиція) = кількість останньої інвентаризації
                 + Σ приходів і повернень після неї
                 − Σ видач і списань після неї
```

Колонка E лишається як кеш для швидкості, але **перераховується** з журналу (а не інкрементується), і розбіжність кешу з перерахунком — сама по собі метрика здоров'я обліку.

## 5.2 Мінімальна модель даних

**Позиція** (додати до аркуша): `ID` (стабільний, прихована колонка — саме він їде в запиті замість номера рядка), `Одиниця`, `Кратність`, `Мінімальна партія (MOQ)`, `Час поставки L, днів`, `Клас критичності`, `Статус` (активна / не використовується / не інвентаризована).

**Подія журналу:** `op_id` (UUID від клієнта — захист від дублів), `час`, `дата операції`, `ID позиції`, `тип`, `кількість`, `одиниця`, `хто`, `де використано`, `посилання на роботу/заявку`, `коментар`.

**Типи операцій** (як у GAS-Миючі:196–204, плюс те, чого бракує там): `Видача (−)`, `Повернення (+)`, `Прихід (+)`, `Інвентаризація (=)`, `Списання браку (−)`, `Коригування (±, з обов'язковою причиною)`.

**Ролі** — за вже записаним у `CLAUDE.md` рішенням: `zip.use` — видача й повернення; `zip.admin` — прихід, інвентаризація, звіт; перевірка PIN **тільки на боці Apps Script**.

**Замовлення** (новий аркуш): `ID позиції`, `кількість`, `дата замовлення`, `постачальник`, `очікувана дата`, `статус`. Без нього неможливо рахувати «у дорозі», а без «у дорозі» будь-яка рекомендація повторюється щодня.

## 5.3 Формули

```
Попит:            d̄  = Σ(видача − повернення придатних) за вікно W / W        [од./день]
                  σ_d = стандартне відхилення денного попиту у тому ж вікні
Цикл поповнення:  L   = час поставки постачальника + T_обробки заявки          [днів]
Страховий запас:  SS  = z × σ_d × √L        — якщо історії достатньо
                  SS  = d̄ × L               — якщо історії мало (правило «подвійного ліду»)
Точка замовлення: ROP = d̄ × L + SS
Рівень поповнення:S   = d̄ × (L + R) + SS,   R — період перегляду (напр. 7 днів)
Доступний запас:  IP  = залишок + у дорозі − зарезервовано
Обсяг замовлення: Q   = ceil( max(0, S − IP) / Кратність ) × Кратність
                  Q   = max(Q, MOQ)   якщо Q > 0
Рекомендувати, якщо IP ≤ ROP  і  немає активного замовлення з ETA раніше, ніж вичерпається запас.
```

Коефіцієнт `z` — за класом критичності, а класифікувати варто **не за вартістю, а за наслідком простою**:

| Клас | Означення | Рівень сервісу | z |
|---|---|---|---|
| A | Зупиняє лінію, аналогів немає, довга поставка | 98 % | 2,05 |
| B | Зупиняє вузол, є обхідний варіант | 90 % | 1,28 |
| C | Витратне, купується за день | 80 % | 0,84 |

Для класу A додатково: `ROP ≥ 1 комплект` завжди, незалежно від статистики.

## 5.4 Чесне застереження про статистику

У журналі за 4 місяці — **9 записів**. Цього не вистачає ні для `d̄`, ні тим паче для `σ_d`. Тому формули з 5.3 — це **ціль**, а не те, що можна ввімкнути завтра. Порядок дій:

1. спершу зробити журнал повним (усі типи рухів) і достовірним;
2. 3–6 місяців працювати за правилом «мін/макс», де мінімум ставить інженер, але вже з урахуванням часу поставки: `мінімум ≥ витрата за час поставки × 1,5`;
3. коли набереться історія — вмикати `d̄`, `SS` і `ROP` за формулами, спершу в режимі «показувати обидві цифри» (стара й нова рекомендація поруч), щоб звірити.

Для більшості ЗІП попит рідкісний і стрибкоподібний (0, 0, 0, 5, 0) — для таких позицій середнє за 30 днів принципово неінформативне; там працює або метод Кростона, або просте правило «страховий запас = максимальна разова витрата за 12 місяців».

## 5.5 Комплекти

```
Довідник:  комплект_ID | компонент_ID | кількість_на_комплект

Попит на компонент = власний попит + Σ (попит на комплект × кількість_на_комплект)
Доступно комплектів = min( по всіх компонентах: floor(залишок_i / кількість_i) )
```

У план закупки виносити не лише дефіцитний компонент, а **весь комплект до рівня N комплектів** — інакше зібрати вузол усе одно не вийде.

## 5.6 Тригери звіту

* Плановий лист — **один раз** на тиждень (понеділок, 08:00) і один щоденний, лише якщо є зміни.
* Терміновий лист — лише **на перетині** порогу (позиція щойно опустилася нижче ROP), не частіше ніж раз на добу на позицію; стан «про що вже сповіщали» зберігати в `PropertiesService`.
* У листі — тільки рядки з реальним дефіцитом, відсортовані за класом критичності; окремим блоком «потребує інвентаризації» (порожній залишок) і «надлишок» (покриття > 12 місяців).

## 5.7 Етапи

Прибрати тестовий запис на 1300 із журналу; заповнити залишки на аркуші «ЗІП»; вирівняти колонки на «Підшипниках» (додати «Залишок на дату» або прибрати її на решті); винести «Інструменти» й «Контейнер та приміщення» в окремий реєстр активів поза логікою закупівель; замінити `-` і `2 (1+1)` на числа або на статус «не використовується»; звести дублі однакових моделей в один рядок; виправити список механіків (APP:131–133).

**Етап 2 — операції та відновлюваний залишок.**

**Етап 3 — планування.**
