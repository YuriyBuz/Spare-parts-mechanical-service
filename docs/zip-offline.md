# Офлайн-режим: черга операцій, синхронізація, вхід без мережі

Документ описує, як застосунок поводиться, коли зв'язку немає або він рветься,
і чому запис у журнал потрапляє рівно один раз.

Стосується файлів `index.html` (клієнт), `sw.js` (service worker) і
`apps-script/Code.gs` (сервер).

---

## 1. Що було не так до цієї зміни

| Проблема | Наслідок на виробництві |
|---|---|
| Черга `zipOfflineQueueV3` — простий масив без статусів | Не видно, що не пішло і чому |
| Запис ставав у чергу лише коли `fetch` кинув помилку | Вкладку закрили в момент запиту → операція зникала |
| Відправка не мала таймауту | Wi-Fi «є, але не працює» → застосунок висів на кнопці |
| Ідентифікатор дубля — лише час операції | Два механіки в ту саму секунду: другий запис вважався дублем і пропадав |
| Без мережі не було входу взагалі | Механік із планшетом у цеху не міг навіть відкрити список |
| Помилку сервера в черзі не було де побачити | `OVERDRAW` з черги мовчки застрягав назавжди |

## 2. Де лежить черга

`localStorage`, ключ **`zipOutboxV1`**:

```jsonc
{
  "version": 1,
  "items": {
    "2026-08-22T18:05:00.000Z-a1b2c3d4-x9k2": {
      "opId":      "2026-08-22T18:05:00.000Z-a1b2c3d4-x9k2",
      "createdAt": "2026-08-22T18:05:00.000Z",
      "payload":   { "action": "registerUsage", "sheetName": "Підшипники", "row": 6,
                     "model": "608-2RSH", "quantity": 1, "location": "Лінія 1",
                     "date": "2026-08-22", "timestamp": "2026-08-22T18:05:00.000Z" },
      "status":    "pending",
      "attempts":  0,
      "nextAttemptAt": 0,
      "lastError": "", "code": "",
      "syncedAt":  null, "serverStock": null, "response": null
    }
  }
}
```

Три принципи:

1. **Токен у черзі не зберігається.** Він додається в момент відправки з поточної
   сесії. Планшет, що пролежав ніч, не надішле запис із протермінованим токеном.
2. **Хто виконав операцію, клієнт не надсилає.** Ім'я підставляє сервер із сесії
   (див. `docs/zip-auth-session.md`), тому підмінити автора з черги неможливо.
3. **У чергу лягає все, навіть онлайн.** Спершу `enqueueOperation()`, і лише потім
   `sendItem()`. Якщо вкладку вб'ють між цими двома кроками — запис уже на диску.

### Статуси

| Статус | Що означає | Що з ним робить застосунок |
|---|---|---|
| `pending` | чекає на відправку | надсилає при першій нагоді |
| `sending` | запит у польоті | якщо висить довше 2 хв (`SENDING_STUCK_MS`) — повертає в `pending` |
| `done` | сервер підтвердив | лишається добу (`OUTBOX_DONE_TTL_MS`), щоб було видно, і зникає |
| `failed` | сервер відмовив по суті | чекає рішення людини, автоматично не повторюється |

`failed` ставиться лише для кодів, які повтором не виправиш:
`FORBIDDEN`, `NOT_FOUND`, `BAD_TARGET`, `NOT_COUNTED`, `OVERDRAW`,
`ALREADY_CANCELLED`, `TOO_LATE` (`PERMANENT_CODES`).
Усе інше — мережа, `BUSY`, п'ятисоті — це `pending` із паузою
5 с → 15 с → 1 хв → 5 хв (`BACKOFF_MS`).

Пауза має сенс, поки причина — мовчання мережі. Тому `resetBackoff()` обнуляє
таймери, коли причина зникла: подія `online`, відкриття сторінки, ручна кнопка
«Синхронізувати». Перервана відправка (`sending` → `pending`) теж іде без паузи:
відповіді не було, чекати немає чого.

### Коли черга рухається

* одразу після постановки запису (`submitUsageBtn`);
* подія `online`;
* повернення на вкладку (`visibilitychange`);
* кожні 30 с, якщо є `pending` (`SYNC_INTERVAL_MS`);
* при завантаженні сторінки, якщо є сесія;
* кнопкою «Синхронізувати» в панелі черги.

Записи йдуть **по одному, в порядку створення**. Перший же провал через мережу
зупиняє цикл: далі однаково не пройде, а порядок операцій по одній позиції важливий.

## 3. Як запис не дублюється

Ідентифікатор операції — `timestamp` (момент натискання кнопки на планшеті).
Він же лягає в колонку A журналу. Сервер перед записом шукає в журналі рядок із
таким часом і, якщо знаходить, нічого не пише:

```js
// Code.gs, registerOperation_()
const duplicate = findLogEntry_(log, payload.timestamp,
  { sheetName: payload.sheetName, model: payload.model, actor: session.name });
if (duplicate) {
  return { success: true, duplicate: true, actor: session.name,
           newStock: readStock_(sheet, payload.row).value };
}
```

Відповідь — **успішна**, з позначкою `duplicate: true`. Клієнту не треба
відрізняти «щойно записали» від «уже було записано»: в обох випадках запис у
журналі рівно один, а `newStock` актуальний.

Збіг часу сам по собі дублем не робить: `findLogEntry_()` звіряє **трійку
«час + позиція + автор»**. Два механіки, що списують ту саму позицію в ту саму
секунду, — це дві різні операції, і обидві потраплять у журнал.

Уся перевірка й запис виконуються під `LockService.getScriptLock()`, тож два
планшети не можуть прочитати той самий залишок одночасно.

## 4. Що бачить механік

**Плашка вгорі екрана** (`#networkStatusBtn`) — єдиний індикатор стану:

| Вигляд | Коли |
|---|---|
| зелена «Онлайн» | черга порожня, зв'язок є |
| зелена «Офлайн-режим» | вхід був локальний, сервер ще не підтверджував сесію |
| синя «Синхронізація…» | іде відправка |
| синя «Черга 3» | 3 записи чекають |
| червона «Помилок 1» | сервер відмовив, потрібне рішення |
| червона «Немає зв'язку» | браузер повідомляє про офлайн |

**Натиск на плашку відкриває панель черги**: кожен запис із позицією, кількістю,
часом, статусом і текстом помилки. Кнопки:

* **Надіслати** — спробувати зараз, не чекаючи паузи;
* **Виправити** — для `failed`. Для `OVERDRAW` пропонує «списати наявні N шт»,
  «списати понад залишок і пояснити» або «лишити в черзі»; для `NOT_COUNTED` —
  перейти до інвентаризації;
* **Видалити** — з підтвердженням і прямим попередженням, що запис у журнал не потрапить.

**Картка позиції** з невідправленою операцією має позначку `⏳ очікує відправки`.

**Історія** показує записи з черги поруч із журналом сервера (`localHistoryRecords()`),
щоб механік бачив своє списання одразу, а не після синхронізації.

Ще до постановки в чергу застосунок звіряє кількість із **кешованим** залишком і
попереджає: «Зв'язку немає, а за останніми даними на складі 5 шт — ви списуєте 9.
Запис збережеться, але сервер може його відхилити».

## 5. Вхід за PIN без мережі

Повний список співробітників і самі PIN на пристрій, як і раніше, не потрапляють.
Після **успішного входу онлайн** застосунок зберігає в `zipOfflineUnlockV1` лише
перевірник:

```jsonc
{ "salt": "…16 байт…",
  "hash": "PBKDF2-SHA256(PIN, salt, 150000)",
  "verifiedAt": 1787430001877,
  "name": "…", "shortName": "…", "roles": [...], "permissions": [...] }
}
```

PIN не зберігається — зберігається похідна, яку перебрати на 4 цифрах коштує
150 000 ітерацій на спробу. Похідна рахується **у фоні**, вже після того, як
застосунок відкрився: користувач не чекає на криптографію.

Обмеження локального входу:

* діє **7 діб** від останнього входу онлайн (`UNLOCK_MAX_AGE_MS`);
* тільки на **тому пристрої**, де вхід був онлайн;
* сесія — **12 годин** (`OFFLINE_SESSION_MS`);
* дозволені лише операції запису: `registerUsage`, `registerRestock`,
  `registerInventory` (`OFFLINE_PERMISSIONS`). Звіт, скасування і зміна місця
  зберігання потребують сервера й лишаються недоступними;
* усе, що зробили офлайн, сервер **однаково перевіряє за ролями** під час
  синхронізації: локальний вхід не дає прав, яких немає в довіднику.

Роль у шапці показується як `admin · офлайн-режим`, щоб не було ілюзії, що
сесія підтверджена сервером.

## 6. Сценарії з постановки задачі

### Механік списав без зв'язку → зв'язок з'явився

1. Кнопка «Видати» → `enqueueOperation()` → `sendItem()` падає на таймауті 8 с.
2. Діалог: «Немає зв'язку. Запис збережено на пристрої й надійде автоматично».
3. Плашка стає «Черга 1», картка позиції — `⏳ очікує відправки`.
4. З'явився Wi-Fi → подія `online` → `resetBackoff()` → `flushOutbox()` →
   запис іде з токеном → `status: done`, тост «Надіслано 1 запис» → `fetchData()`.
5. У журналі — один рядок.

### Планшет перезавантажили з незбереженими операціями

Черга в `localStorage`, тому переживає і перезавантаження, і повне вимкнення.
При старті: `migrateLegacyQueue()` (переносить записи зі старого ключа
`zipOfflineQueueV3`), `resetBackoff()`, потім `flushOutbox()` — але **лише якщо
сесія жива**. Інакше на екрані входу з'явиться пояснення: «Зв'язок відновлено —
увійдіть за PIN, щоб надіслати збережені записи».

Окремий випадок — вкладку вбили **в момент запиту**, статус лишився `sending`.
Сервер міг записати операцію, а міг і ні. `pruneOutbox()` через 2 хвилини
повертає такий запис у `pending` і надсилає ще раз; якщо він уже в журналі,
сервер відповість `duplicate: true` і другого рядка не з'явиться.

### Два механіки списують ту саму позицію одночасно

* Обидва записи потрапляють у журнал (різні автори → не дубль).
* Залишок рахується з журналу під загальним замком, тому зменшується двічі.
* Якщо на другого вже не вистачає, він отримує `OVERDRAW` з реальною доступною
  кількістю — від'ємний залишок мовчки не пишеться. Запис лишається в черзі зі
  статусом `failed`, і механік у панелі черги вибирає: списати наявні, списати
  понад залишок із поясненням, або видалити.

### Вхід за PIN, коли зв'язку немає взагалі

Сторінка відкривається з кешу service worker'а (навігація: мережа з таймаутом
3 с, далі — збережена сторінка). PIN звіряється з локальним перевірником,
застосунок відкривається з каталогом із `zipInventoryCacheV3` і правом писати
операції. Якщо онлайн-входу на цьому пристрої ще не було — чесне повідомлення:
«Немає зв'язку. Локальний вхід недоступний — спершу увійдіть один раз онлайн».

## 7. Ключі в localStorage

| Ключ | Що зберігає | Час життя |
|---|---|---|
| `zipSessionV1` | токен, ім'я, ролі, права | до `expiresAt` |
| `zipOfflineUnlockV1` | сіль + PBKDF2 від PIN, ім'я, ролі | 7 діб |
| `zipOutboxV1` | черга операцій | `done` — доба, решта — до відправки |
| `zipInventoryCacheV3` | каталог позицій | до наступного `fetchData()` |
| `zipDeviceIdV1` | ідентифікатор пристрою (прив'язка токена) | постійно |
| `zipLastActivityV1` | час останньої дії (автовихід 10 хв) | постійно |
| `zipPeopleV1` | довідник для підказок у полях | до наступного завантаження |
| `zipOfflineQueueV3` | стара черга | переноситься в `zipOutboxV1` і видаляється |

## 8. Перевірено тестами

Серверна частина (мок Apps Script на реальних даних таблиці):

* повторна доставка тієї самої операції не списує вдруге, у журналі один рядок;
* збіг часу у двох механіків не робить другий запис дублем — два рядки, різні автори;
* збіг часу на іншій позиції теж не дубль;
* гонка за останню штуку: другий отримує `OVERDRAW`, а не від'ємний залишок;
* застарілий запис із черги понад залишок у журнал не потрапляє.

Клієнт (Chromium):

* офлайн-списання лягає в чергу зі статусом `pending` і **без токена**;
* після `online` запис іде **рівно один раз**; повторна синхронізація не надсилає вдруге;
* після перезавантаження сторінки запис надсилається автоматично, один раз;
* зависла відправка (`sending`) повертається в чергу й доходить один раз;
* попередження про перевитрату за кешем ще до постановки в чергу;
* `OVERDRAW` у черзі видно в панелі, «Виправити» → «Списати наявні» доводить запис;
* офлайн-вхід: невірний PIN не пускає, правильний відкриває застосунок у режимі
  «офлайн» без права на звіт, каталог показується з кешу.
