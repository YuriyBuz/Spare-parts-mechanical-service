# Еталонна структура таблиці чек-листа

**Статус: схвалено й реалізовано.** Код — у `apps-script/`, довідка й порядок запуску —
у [`checklist-schema.md`](./checklist-schema.md). Таблиця не змінена: скрипти запускаєте ви.

> Кілька цифр нижче уточнені після повного прогону парсера: відповідей **12 615** (а не 12 582),
> чек-лист майстра відновлено **повністю — 30 пунктів із 30**, виведених з ужитку пунктів **10**,
> `item_id` отримали **100%** відповідей. Деталі — у `checklist-schema.md`, розділ 4.

---

## 1. Принципи

1. **Один факт — один рядок.** Замість 352 текстових блоків — 12 615 рядків відповідей, кожен із яких можна відфільтрувати, порахувати й нанести на графік.
2. **Довідники окремо від фактів.** Що перевіряємо, які варіанти відповіді, що є нормою — в довідниках. Що відповіли — у фактах. Змінити норму не означає переписати історію.
3. **Нічого не видаляємо.** `Лист1` залишається недоторканим. Історичні статуси зберігаються поряд із перерахованими.
4. **Ідентифікатори замість тексту.** `item_id`, `user_id`, `report_id` — стабільні. Переформулювання пункту не рве історію.
5. **Ідемпотентність.** Повторний запуск міграції або повторна відправка звіту не створюють дублів.

## 3. Аркуші

### `01_Пункти` — довідник того, що перевіряємо

| Колонка | Тип | Приклад |
|---|---|---|
| `item_id` | текст, ключ | `mech.1-1` |
| `role` | список | `Механік` / `Майстер` |
| `group_id` | текст | `compressor` |
| `group_title` | текст | `1. Компресорне приміщення` |
| `seq` | число | `1` |
| `text` | текст | `Температура компресорів` |
| `type` | список | `binary` / `number` / `text` |
| `unit` | текст | `°C` |
| `labels` | текст | `№1;№2` |
| `fields` | число | скільки числових полів (0 для кнопок) |
| `norm_min_1..3` / `norm_max_1..3` | число | межа сигналу на кожне поле |
| `warn_min_1..3` / `warn_max_1..3` | число | межа попередження |
| `visible_on` | список | `all` / `start` / `end` |
| `photo_required` | так/ні | `ні` |
| `active_from` | дата | `2026-03-24` |
| `active_to` | дата | порожньо = діє |
| `text_aliases` | текст | історичні формулювання через `;` |
| `notes` | текст | |

**`norm_min_N`/`norm_max_N` порожні = сигнал не спрацьовує.** Це навмисно: поки технолог не заповнить норми, система поводиться як зараз і не створює хибних тривог.

### `02_Варіанти` — норма для кнопкових пунктів

| `item_id` | `seq` | `value` | `status` | `active` |
|---|---|---|---|---|
| `mech.1-3-end` | 1 | `Увімкнено` | `ok` | так |
| `mech.1-3-end` | 2 | `Не потр.` | `ok` | так |
| `mech.7-9` | 1 | `Так` | `ok` | так |
| `mech.7-9` | 2 | `Ні` | `alert` | так |
| `mech.1-2` | 91 | `Немає` | `ok` | ні |

`active = ні` — історичне написання варіанта: у застосунку не показується, але міграція його впізнає.

Це та таблиця, що прибирає 77 хибних тривог: «Не потр.» перестає бути аварією тому, що так написано в довіднику, а не тому, що воно стоїть у масиві останнім.

`report_id` детермінований (хеш від `ts_server` + автор + стадія) — повторний запуск міграції або повтор із офлайн-черги не створять другого рядка.

`cnt_alert` — те, чого система не рахувала жодного разу за пів року.

### `12_Відповіді` — головна таблиця, 1 рядок = 1 пункт у 1 звіті

| Колонка | Тип | Приклад |
|---|---|---|
| `answer_id` | ключ | `2026-03-01_mech_start_a3f91c#12` |

| `item_id` | посилання | `mech.7-9` |
| `item_text_snapshot` | текст | формулювання на момент звіту |
| `seq` | число | порядок у звіті |

**Дві колонки статусу — свідомо.** `status_original` зберігає історичну оцінку, `status` — перераховану за новими правилами. Нічого не переписується, а різниця між ними одразу показує ефект виправлення.

Числа з текстових полів витягуються в `value_num_*`, оригінал завжди лишається у `value_text`.

Заповнюється щодня тригером. `status` = `ok` / `пропущено` / `дубль`. Саме те, чого бракує: 13 порожніх днів і 18 напівднів більше не пройдуть непоміченими.

## 7. Гарантії збереження даних

1. **Резервна копія всього файлу** перед будь-якою дією — окремий документ `check-list-mechanic (backup 2026-08-23, перед міграцією структури)`, за тією ж домовленістю, що ви застосували для ЗІП.
2. **`Лист1` не змінюється взагалі** — ні перейменування, ні сортування, ні видалення, ні нових колонок. Міграція читає його і не пише в нього.
3. **Усі нові аркуші — додаткові.** Наявні формули, посилання й закладки продовжують працювати.
4. **Кожен мігрований рядок несе `raw_row`** — номер вихідного рядка в `Лист1`. Будь-яке число можна звірити з оригіналом за секунду.
5. **Міграція ідемпотентна**: `report_id` детермінований, повторний запуск не дублює й не псує.
6. **Перехідний період**: новий бекенд пише і в нову структуру, і в `Лист1` у старому форматі. Вимикаємо старий запис тільки після того, як переконаємось, що все на місці.
7. **Звірка після міграції** — автоматична: 352 звіти, 12 615 відповідей, 777 фото, контрольні суми за статусами. Розбіжність = міграція не зараховується.
