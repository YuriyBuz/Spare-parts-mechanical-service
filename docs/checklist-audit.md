## 1. Як воно працює зараз

### 1.1 Архітектура

### 1.2 Конфігурація

`checklistConfig` — 7 груп (Компресорна, Свердловини, Генератор, Котельні, Холодильний контейнер, Виробничі зони, ХВО). Кожен пункт має:

- `type` — `binary` (кнопки-варіанти), `input` (одне поле), `dual_input` (два поля);
- `visibleOn` — `all` / `start` / `end`, тобто пункт показується на початку зміни, в кінці, або завжди;
- необов'язкові `photoRequired`, `hasTooltip`, `unit`, `labels`.

Розподіл у поточній версії: **36 пунктів `binary`, 4 `input`, 3 `dual_input`**. Секція «Початок зміни» = 38 пунктів, «Кінець зміни» = 39.

### 1.3 Як рахується «Виконано X з Y» 🟢

Це єдиний числовий показник, який система рахує. Логіка (`index.html:1162-1163`):

```js
const items = Array.from(document.querySelectorAll(`#${section}ShiftSection .checklist-item`));
const total = items.length;
const completed = items.filter(i => i.classList.contains('completed')).length;
```

**`completed` — це CSS-клас, який означає «до поля торкнулися».** Він вішається так:

| Тип | Коли ставиться `completed` |
|---|---|
| `binary` | натиснуто **будь-який** варіант (`:777`) |
| `input` | у полі **будь-який** непорожній текст (`:790`) |
| `dual_input` | заповнене **хоча б одне** з двох полів (`:812`) |

Далі `summary: \`Виконано ${completed} з ${total}\`` летить на сервер **рядком** і так само рядком лягає в колонку таблиці.

Ключове: з 24.03.2026 відправка неповного чек-листа **заблокована** (`:1128-1143`) — якщо не всі пункти заповнені, кнопка перетворюється на «Заповнити пропущені пункти» і нічого не відправляє.

> Це підтверджують дані: останній неповний звіт — **23.03.2026**, далі всі 298 звітів мають `X == Y`.

Наслідок, який варто усвідомити: **показник «Виконано X з Y» за конструкцією завжди дорівнює «N з N»**. Він п'ять місяців поспіль повідомляє одне й те саме і не несе жодної інформації.

### 1.4 Як визначається «НЕ НОРМА» 🟢

Другий і останній аналітичний механізм. Пункт вважається аварійним, якщо на ньому стоїть клас `.selected-bad`. А клас призначається **за позицією варіанта в масиві** (`:591-598`):

```js
let kind = 'good';
if (item.options.length === 3) {
    if (index === 1) kind = 'bad';
    if (index === 2) kind = 'neutral';
} else {
    if (index === item.options.length - 1) kind = 'bad';   // останній = поганий
}
```

Тобто:

- для двох варіантів «поганим» є **останній**;
- для трьох — **другий**;
- для `input` і `dual_input` (температури, тиски, напруга) поняття норми **не існує взагалі**.

Далі бекенд малює `❗ ❌` замість `✅` і фарбує рядок у листі червоним. І все — ніякого підрахунку, порогу чи ескалації.

### 1.5 Фото

Клієнт стискає знімок до ширини 800 px, JPEG q0.7, у base64 (`:686-728`) і кладе в об'єкт `currentPhotos` **у пам'яті вкладки**. Усі фото їдуть одним JSON разом зі звітом.

Бекенд для кожного фото робить три речі: інлайн-картинку для листа, вкладення до листа, і файл у папці Drive із доступом `ANYONE_WITH_LINK`.

### 1.6 Збереження стану й офлайн

`saveState()` (`:865-879`) пише в `localStorage` три поля на пункт: `completed`, `value`, `comment`. Плюс вибраного механіка й тему.

Офлайн-звіт кладеться в чергу `offlineReportsQueue` і відправляється при події `online`.

### 1.7 Що лягає в таблицю

**Третій — 78 разів заслінки вентиляції залишили відкритими** на кінець зміни, тобто приблизно кожну другу зміну. Або це системне порушення, на яке ніхто не зреагував за пів року, або пункт сформульований так, що правильної відповіді немає. Дані не дозволяють відрізнити — і це теж проблема.

### 2.2 322 виміри температури компресорів. Норми немає

Зафіксовано 322 пари показників, діапазон **від 12 до 90 °C**. Значення `[№1: 55 / №2: 89]` записане як `✅`. Жоден вимір за пів року не викликав жодної реакції системи, бо для `dual_input` перевірок не існує.

Те саме стосується тиску пари, тиску води вхід/вихід, тиску повітря і напруги в мережі.

### 2.3 134 фото втрачено (17%)

У звітах **643** робочі посилання на Drive і **134** записи `Помилка фото`. Причина в самому тексті помилки:

```
Exception: У доступі відмовлено: DriveApp.
Exception: У вас нет разрешения на вызов функции "DriveApp.Folder.createFile".
```

Скрипт періодично втрачає авторизацію Drive. Саме для цього у файлі є функція `doAuth()` — тобто проблему знають і лікують уручну, повторно авторизуючи скрипт.

Що при цьому бачить механік: **«✅ Успішно! Звіт відправлено»**. Що бачить інженер у таблиці: рядок `🔗 Помилка фото: Exception…` посеред звіту. Фото, найімовірніше, все ж потрапило в лист (інлайн-картинка створюється **до** блоку Drive), але в архіві його немає і посилання немає.

### 2.4 Пропуски й дублі, яких ніхто не бачив

За 178 календарних днів від першого до останнього звіту:

## 3. Проблеми

**P0** — система не виконує своєї функції або втрачає дані · **P1** — регулярно дає хибний результат · **P2** — обмежує звітність · **P3** — гігієна.

### P0 — критичні

#### P0-1. «НЕ НОРМА» нікуди не веде

Це головна проблема. Чек-лист існує, щоб вчасно ловити відхилення. Він їх ловить — 303 штуки за пів року — і **зупиняється на цьому**: жодного підрахунку, порогу, порівняння з учора, ескалації чи хоч би окремого рядка «сьогодні 3 відхилення» у листі.

Кожне відхилення — один рядок у одному з 352 листів і фрагмент тексту в одній комірці. Щоб побачити «UF-лампа не світить 18 разів», треба зробити те, що зробив цей аудит: вивантажити всю таблицю і розпарсити текст.

Практичний наслідок: **система збирає дані про несправності, але не повідомляє про несправності.**

#### P0-2. Правило «останній варіант = поганий» дає 25% хибних тривог

Механізм із `:591-598` не описує норму — він описує **порядок кнопок**. Наслідки вже в даних:

- `['Увімкнено', 'Не потр.']` → «Не потр.» аварія. **77 хибних спрацювань.**
- Переставити варіанти місцями в конфігу — і аварія стане нормою. Мовчки, без жодного сліду.
- Три варіанти трактуються як «good / bad / neutral» за індексом: `['Норма', 'Сторонній шум', 'Генератор не запущений']` працює тільки тому, що хтось вгадав порядок.

Коли чверть сигналів — шум, люди перестають дивитися на всі сигнали. Це пояснює, чому 78 разів відкриті заслінки нікого не зупинили.

#### P0-3. Для числових пунктів норми не існує

7 пунктів (`input` + `dual_input`) збирають температури, тиски й напругу. Для них `isBad` **не обчислюється в принципі** — будь-яке значення це `✅`.

322 виміри температури компресорів у діапазоні 12–90 °C пройшли без єдиного зауваження. Пункт «Виміряти показники напруги» зі значенням `200` — `✅`. Пункт «Зняти показники з табло» зі значенням `Поилка PN-12` (тобто механік вручну написав, що є помилка) — теж `✅`.

Найважливіші параметри обладнання — єдині, які система не контролює взагалі.

#### P0-4. Втрата фото: 134 випадки, «Успішно» на екрані

Розібрано в §2.3. Три окремі дефекти складаються:

1. Авторизація DriveApp злітає → `createFile` кидає виняток.
2. Виняток ловиться і **перетворюється на рядок тексту** всередині звіту — не на помилку, не на сигнал.
3. Клієнт через `mode:'no-cors'` не бачить нічого і показує «✅ Успішно».

Фото при цьому існувало тільки в пам'яті вкладки — після відправки воно втрачене остаточно.

#### P0-5. `mode: 'no-cors'` — клієнт ніколи не знає, чи звіт дійшов

`:1224` і `:1021`:

```js
await fetch(GOOGLE_SCRIPT_URL, { method:'POST', mode:'no-cors', ... });
clearSectionData(section);              // ← стираємо все заповнене
status.textContent = '✅ Успішно! Звіт відправлено.';
```

При `no-cors` відповідь непрозора: проміс успішний, навіть якщо скрипт упав, вичерпав квоту або повернув `{result:'error'}`. Одразу після цього **`clearSectionData` стирає всі відповіді й фото**.

Тобто у разі помилки на сервері механік втрачає всю зміну роботи і не дізнається про це.

Те саме в `processOfflineQueue` (`:1010-1037`) — елемент видаляється з черги без підтвердження, а наприкінці показується «Всі офлайн звіти успішно відправлено!», чого код перевірити не може.

#### P0-6. Немає контролю, що чек-лист узагалі заповнили

13 днів без звітів і 18 днів з однією зміною замість двох (§2.4) пройшли непоміченими. Немає ні розкладу, ні очікуваних змін, ні нагадування, ні сигналу «звіту немає».

Для системи змінного контролю це означає, що вона гарантує рівно нічого: заповнений чек-лист свідчить лише про те, що хтось його заповнив.

#### P0-7. Немає ідемпотентності — 36 дублів у даних

Звіт не має ідентифікатора. Офлайн-черга повторює відправку, якщо мережа обірвалася після запису. У даних — 36 пар «день + зміна» з кількома звітами, до 5 за один ранок.

Який із п'яти звітів за 17.04.2026 правильний — визначити неможливо.

### P1 — регулярно дають хибний результат

#### P1-1. «Виконано X з Y» не означає нічого

Три причини разом:

1. З 24.03.2026 неповний звіт не відправляється → показник **завжди** «N з N».
2. `completed` = «поле торкнулися», а не «пункт у нормі».
3. `Y` мінявся 6 разів (37 → 35 → 38 → 39), і версія ніде не збережена — «38 з 38» у березні й у серпні це різні чек-листи.

Показник зберігається текстом, тож навіть побудувати з нього графік не вийде без парсингу.

#### P1-2. Фото не переживають перезавантаження сторінки

`saveState()` зберігає `completed`, `value`, `comment`. **`currentPhotos` не зберігається ніде** (`:526`).

Механік ходить по цеху з телефоном — вкладка вивантажується. Після повернення всі відповіді на місці, фото зникли. Валідація `photoRequired` це помітить і не дасть відправити — тобто механік просто мовчки переробляє роботу, не розуміючи, чому «фото пропало».

Гірший варіант: перемикання вкладки «Початок» ⇄ «Кінець» викликає `renderChecklist`, який **повністю перебудовує DOM** (`:531`), а `restoreDOMState` мініатюри фото не відновлює. Дані в пам'яті ще є, але інтерфейс показує, що фото немає. Механік перефотографує — і перезапише.

#### P1-3. Гонка при додаванні фото

`handlePhotoUpload` асинхронний: `FileReader.onload` → `img.onload` → тільки тоді `currentPhotos[uniqueId] = dataUrl`. Функція повертається негайно.

Якщо натиснути «Перевірити та відправити» одразу після вибору фото (велике фото з камери обробляється помітно довго), звіт піде без нього. Індикації обробки немає.

#### P1-4. `getActiveSheet()` замість `getSheetByName()`

```js
var sheet = SpreadsheetApp.getActiveSheet();
```

Аркуш зараз один і називається `Лист1` — тому працює. Щойно з'явиться другий (а він потрібен для будь-якої звітності), звіти почнуть падати в довільну вкладку. Міна, яка спрацює один раз і тихо.

#### P1-5. Одержувачі й роль приходять із клієнта

```js
var role = data.role || "Механік";
var recipients = data.recipients || 'Buznitskiy7@gmail.com,...';
```

Ані те, ані інше не перевіряється. Хто знає URL скрипта (а він у публічному HTML на GitHub Pages) — розсилає листи з поштової скриньки власника на будь-які адреси, з вкладеннями, поки не вигорить квота `MailApp`. Роль «Майстер» підробляється одним полем JSON.

#### P1-6. Запис у таблицю і лист не атомарні

`appendRow` виконується **до** `MailApp.sendEmail`. Якщо лист не піде — виняток вилітає вже після запису рядка: у таблиці звіт є, на пошті немає, клієнт показує «Успішно».

Розмір листа роздутий штучно: кожне фото додається **і як `inlineImages`, і як `attachments`** — подвійний обсяг. При ліміті 25 МБ і 800 px JPEG це десь 100+ фото, але з `photoRequired` на 3 пунктах і можливістю додати фото до **будь-якого** з 38 пунктів запас не такий великий, як здається.

#### P1-7. `tryLock` без перевірки результату

```js
lock.tryLock(30000);   // повертає boolean, який ігнорується
```

Якщо блокування не взяли за 30 секунд, код **однаково виконується далі**. Дві одночасні відправки дадуть два `appendRow` і два листи.

#### P1-8. Дата зберігається як текст із часом усередині

```js
date: new Date().toLocaleString('uk-UA'),   // "01.03.2026, 08:30:12"
time: new Date().toLocaleTimeString('uk-UA')
```

У колонці «Дата» лежить рядок з датою **і** часом, у наступній колонці — час ще раз. Ні відсортувати, ні відфільтрувати, ні побудувати зведену таблицю по датах у Google Sheets не можна без попереднього парсингу.

Плюс дві незалежні мітки часу: `new Date()` на сервері (колонка 1) і `toLocaleString` на клієнті (колонка 2). Вони розходяться на час доставки, а при офлайн-черзі — на години чи дні. Яка з них «час зміни», ніде не визначено.

#### P1-9. Ідентифікація людей рядком, і список уже двічі мінявся

Розібрано в §2.5: три несумісні хардкод-списки в трьох застосунках, «Заміна» як легальний вибір у 26% звітів, нуль перетину поточного списку з історією.

### P2 — обмежують звітність

#### P2-1. Звіт — це текст, а не дані

Уся суть звіту (37–39 відповідей, значення, коментарі, посилання на фото) лежить **одним рядком в одній комірці** з емодзі-розміткою. Наслідки:

- будь-який аналіз вимагає парсингу тексту регулярками (як у цьому аудиті);
- зіставити пункт між звітами можна тільки за **точним текстом формулювання** — а формулювання змінювалися: «Провести зовнішній візуальний огляд **агрегату**» → «…**генератора**», «Оглянути стан димососа» → «Перевірити роботу димососа»;
- `id` пункту (`3-1`, `7-8`), який у конфізі є і стабільний, на сервер **не передається взагалі**;
- ліміт комірки Google Sheets — 50 000 символів; поточні звіти близько 3 000, запас є, але напрямок неправильний.

#### P2-2. Немає заголовків і немає структури таблиці

Аркуш називається `Лист1`, рядка заголовків немає, колонок 7. Людина, яка відкриє таблицю вперше, не зрозуміє, що в них.

#### P2-3. Коментарі є, але їх не видно

У звітах 124 коментарі механіків — саме там найцінніший контекст («Клапан автоматичного набору води в буферну ємність»). Вони поховані всередині того ж текстового блоку, окремої колонки немає, у пошук не потрапляють.

#### P2-4. Фото публічні

```js
file.setSharing(DriveApp.Access.ANYONE_WITH_LINK, DriveApp.Permission.VIEW);
```

Кожне з 643 фото обладнання доступне будь-кому за посиланням. Зберігаються вони в папку `Фото (File responses)` — папку відповідей Google Forms, тобто змішуються з даними іншої системи.

#### P2-5. `MimeType.JPEG` і `photoName` захардкоджені

Ім'я файлу — `перші_20_символів_пункту_дата_час.jpg`, mime завжди JPEG. Прив'язки до звіту, зміни чи обладнання в імені немає, тож у папці з 643 файлами знайти потрібний можна тільки через посилання зі звіту.

#### P2-6. HTML у листі не екранується

`item.text`, `item.comment`, `item.value` підставляються в `htmlBody` шаблонними літералами. Коментар із символом `<` ламає верстку таблиці в листі.

### P3 — гігієна

- **P3-1.** У `checklistConfig` є пункт із **~30 рядками HTML** прямо в об'єкті конфігурації (`tooltipHtml` для термоголовки принтера). Інструкції варто тримати окремо від структури чек-листа.
- **P3-2.** Секції «Початок» і «Кінець» дублюють пункти з різними `id` (`1-3` / `1-3-end`), хоча це той самий об'єкт контролю в двох станах.
- **P3-3.** `employeeSelect.value.split(' ')[1]` для звертання на ім'я — на «Заміна» дасть `undefined` і впаде на fallback.
- **P3-4.** `updateClock` оновлюється раз на 60 с через `setInterval`, але при поверненні з фону не синхронізується.
- **P3-5.** Тема оформлення зберігається в тому ж об'єкті, що й відповіді чек-листа (`STORAGE_KEY`), тобто очищення стану скидає і тему.
- **P3-6.** Версія застосунку ніде не фіксується — ні в коді, ні у звіті.

## 5. Рекомендована цільова логіка

### 5.1 Головне: норму треба описати явно

Замість «поганий = останній у списку» — явна декларація в конфізі:

```js
// binary
{ id:'1-3-end', text:'Увімкнути систему нічного обігріву',
  type:'binary',
  options:[
    { val:'Увімкнено', status:'ok'      },
    { val:'Не потр.',  status:'ok'      },   // ← більше не хибна тривога
    { val:'Не вдалося',status:'alert'   }
  ] }

// числові — з діапазоном
{ id:'1-1', text:'Температура компресорів', type:'dual_input',
  unit:'°C', norm:{ min:0, max:75 },                 // поза діапазоном → alert
  labels:['№1','№2'] }

{ id:'4-1', text:'Тиск пари', type:'dual_input',
  unit:'бар', norm:{ min:4, max:8 }, required:true }
```

Три статуси замість двох: `ok` / `warn` / `alert`. `warn` — потребує уваги, `alert` — потребує дії сьогодні.

Це одночасно закриває P0-2 (хибні тривоги зникають) і P0-3 (числа нарешті контролюються). За наявними даними це дало б: −77 шумових сигналів і щонайменше кілька десятків нових справжніх на температурах.

### 5.2 Звіт як дані, а не як текст

Замість одного текстового блоку — **рядок на пункт** в окремому аркуші `Відповіді`:

| report_id | ts | business_date | shift | user_id | item_id | item_version | value | status | comment | photo_url |
|---|---|---|---|---|---|---|---|---|---|---|

і аркуш `Звіти` з шапкою:

| report_id | ts | business_date | shift | user_id | config_version | всього | ok | warn | alert | фото_очікувалось | фото_збережено |

Після цього «UF-лампа не світить 18 разів за пів року» — це один `COUNTIFS`, а не аудит.

`item_id` (`7-9`) уже існує в конфізі й стабільний — його просто треба почати передавати. Це закриває P2-1 і робить можливим порівняння між версіями чек-листа (P1-1).

### 5.3 Показники, які варто рахувати замість «X з Y»

| Показник | Навіщо |
|---|---|
| `alert` за зміну / за тиждень | те, заради чого існує чек-лист |
| Топ-5 пунктів з `alert` за 30 днів | знайшов би UF-знезараження і заслінки за перший тиждень |
| Повторні `alert` на тому ж пункті N змін поспіль | ескалація керівнику |
| Пропущені зміни | закриває P0-6 |
| Частка фото, що збереглися | закриває P0-4 |
| Час заповнення (перший дотик → відправка) | виявляє «протикування» чек-листа за 40 секунд |

Останнє варто підкреслити: зараз неможливо відрізнити сумлінний обхід від проставляння кнопок сидячи. Мітка часу першої взаємодії це показує.

### 5.4 Надійна доставка

1. `report_id = crypto.randomUUID()` генерується **при створенні звіту**, не при відправці.
2. Бекенд перевіряє `report_id` перед записом; дубль → `{ok:true, duplicate:true}` без другого рядка й другого листа. Закриває P0-7.
3. Прибрати `mode:'no-cors'`: не ставити власний заголовок `Content-Type` (браузер надішле `text/plain`, preflight не виникає), відповідь стає читабельною.
4. **`clearSectionData` викликати тільки після `ok:true`.** Зараз форма стирається до будь-якого підтвердження — це P0-5 у чистому вигляді.
5. Фото зберігати в `IndexedDB` разом зі станом (P1-2), у `handlePhotoUpload` показувати індикатор обробки і блокувати відправку до завершення (P1-3).

### 5.5 Фото

- Зберігати в Drive **до** формування листа; при помилці повертати `ok:false` з причиною, а не рядок тексту у звіті.
- Доступ — по домену/групі, не `ANYONE_WITH_LINK` (P2-4).
- Ім'я файлу: `{business_date}_{shift}_{item_id}_{report_id}.jpg` (P2-5).
- У листі залишити **або** інлайн, **або** вкладення, не обидва (P1-6).
- Вирішити проблему авторизації Drive системно: перевіряти доступ на початку `doPost` і повертати зрозумілу помилку, а не втрачати 17% фото мовчки.

### 5.6 Люди, зміни, час

- Аркуш `Працівники`: `user_id`, ПІБ, ролі, активний/неактивний. Прибрати «Заміна» як варіант — якщо працює підмінний, у нього має бути своя картка.
- `role` і `recipients` брати **тільки** з таблиці за `user_id`, ніколи з клієнта (P1-5).
- Один канонічний `ts` в ISO-8601 UTC (ставить сервер) + окремі `business_date` (`Europe/Kyiv`) і `shift` (`день`/`ніч`). Нічна зміна цілком належить даті свого початку (P1-8).
- Розклад очікуваних змін → щоденна перевірка «звіт за зміну є?» → нагадування механіку, потім керівнику (P0-6).

### 5.7 Серверна надійність

```js
const lock = LockService.getScriptLock();
if (!lock.tryLock(30000)) {
  return json({ ok:false, retryable:true, error:'busy' });
}
try {
  const sheet = ss.getSheetByName('Відповіді');   // не getActiveSheet()
  // 1) записати дані  2) тільки потім побічні ефекти
} finally { lock.releaseLock(); }
```

Порядок операцій: спершу запис даних, потім лист. Невдала розсилка не повинна виглядати як невдалий звіт і навпаки (P1-6, P1-7, P1-4).

### 5.8 Версіонування конфігурації

`config_version` (наприклад хеш `checklistConfig`) писати в кожен звіт. Тоді «38 з 38» у березні й у серпні перестануть виглядати однаково, а зміну формулювання пункту можна буде відстежити (P1-1, P2-1).

І винести обидва Apps Script у git через `clasp` — зараз серверна логіка існує в єдиному екземплярі всередині Google, без історії змін.
